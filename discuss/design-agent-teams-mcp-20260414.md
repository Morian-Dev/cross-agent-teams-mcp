## 问题陈述

同时运行多个 code agent (opencode + GLM-5.1, Claude Code + Opus 4.6, Codex CLI + GPT-5.4) 并行开发项目时, 各 agent 完全无法感知彼此的工作. 用户手动承担"中间人"角色: 后端 agent 改了 API schema, 需要用户手动把新定义 copy 给前端 agent, 频繁漏传或传旧版.

首要楔子场景: **前后端并行开发时的接口契约同步**. 其他场景 (跨 agent 代码互评, 任务 handoff, 群聊协作) 保留为未来扩展.

## 为什么这事酷

- **MCP 是唯一的通用插口**: opencode / Claude Code / Codex CLI 都支持 MCP. 一个 MCP server 就能让三个不同厂商的 agent 通话, 不用为每个 agent 写 adapter.
- **多模型协作是 2026 年的真实需求**: GLM-5.1 / Opus 4.6 / GPT-5.4 各有所长, 让它们在同一项目里分工协作, 是单 agent 单模型做不到的.
- **借用已验证的抽象**: Claude Code 的 agent teams 模式 (team lead + teammates + shared task list + mailbox) 已经跑通了一版, 直接移植到跨 agent 版本可以跳过架构摸索期.

## 约束

- **语言**: TypeScript + Fastify (MCP 生态 TS SDK 最成熟). 后期性能不够再评估 Rust axum 重写.
- **分发**: npm package, `npx ts-agent-teams` 启动 daemon. 不做二进制分发, 不做 auto-update.
- **存储**: 本地 SQLite (唯一的持久化来源, 所有表全部在 SQLite 内), 默认 `~/.ts-agent-teams/`. SQLite 开启 WAL + busy_timeout=5000. 统一 `events` outbox 表承担审计日志 + 订阅分发双重职责; JSONL 已废弃.
- **传输层 (锁死)**: MCP "Streamable HTTP" transport 为**唯一支持**方式. 原因: 多个 agent 必须共享同一个长驻 daemon, stdio 是 1:1 client-server, 共享不了. SSE 是该 transport 的 server→client 推送通道, 假设所有 MCP client 支持 streamable-HTTP spec (官方标准). 阶段 0 第 1 步验证三家 client 都能连上, 验证失败的 Plan B: 给该 agent 提供 "stdio-proxy" 补丁 - 一个极轻的本地 stdio MCP 进程, 只做 HTTP 透传到 daemon.
- **agent 身份**: `agent_id` 由 MCP SDK 为每次 session 自动分配的 session UUID, **人不指定**. 因此天然全局唯一, 碰撞即 daemon bug, 检测到 → 返回 409 并记日志. human 只需要在 MCP server 配置里指定 `role` (如 `frontend` / `backend`) 和可选 `display_name`, 这些作为 `register_agent` 的入参, 用于寻址和展示.
- **寻址**: 直接消息可以用 `agent_id` (临时精确) 或 `role` (稳定模糊). `send_message({ to_role: 'frontend', body })` 送给当前在线且 role='frontend' 的**所有** agent. 消息也是入 events 表再 fan-out, 保证离线补齐.
- **`last_seen_at` 机制**: 每次该 agent 调任何 MCP tool 时, daemon 顺手更新 `agents.last_seen_at`. 无独立 heartbeat, 无 tool 调用的 agent 视为 idle.
- **Team 作用域 (MVP 就支持)**: 每张表加 `team` 列, 默认 `'default'`. human 在 MCP server 配置里可指定 `team='project-a'` 做多项目隔离, 不指定就走 default. 所有查询 WHERE team 过滤, 防止 cross-project 消息泄漏. 切成本: 约 6 行 SQL + 1 个参数.
- **事件幂等**: 所有 events 表行都有 `event_id INTEGER PRIMARY KEY AUTOINCREMENT` 单调递增. client 侧保留 `last_processed_event_id` cursor, 每次 polling 传 `since: last_processed_event_id`, SSE 收到也更新. 服务端从不主动去重, 由 client 的 cursor 保证不重复消费.
- **events 表生命周期**: 加索引 `idx_events_team_id (team, event_id)` 保证翻页 O(log n). daemon 内部 `setInterval` 每 1 小时跑一次清理, 删除 `created_at < now() - 7 days` 的行. 理由: agent team 对话时效性强, 超过 7 天的状态没价值; 若 agent 需要更老的状态直接查 `contracts` / `tasks` / `agents` 当前态表即可 (这些不会被清). `contracts` 表本身是 schema 演化历史 (按 version 保留), **不受 7 天清理影响**.
- **安全边界**: daemon 仅监听 `127.0.0.1`, 默认无 auth (本机信任模型). 可选 `--token` 启用 bearer 鉴权 (Authorization header 或 query string 传递). 不开远程监听.
- **测试**: 功能测试放独立测试文件 (项目 CLAUDE.md 规定), 不混在正常代码里.
- **编码风格**: 行宽 ≤88, 文件 ≤800 行, 多个小文件优于大文件, 不可变性优先.

## 前提 (已用户确认)

1. 多 agent 并行工作时彼此盲视是真实痛点 (用户直述: "前后端两个 agent 开发时完全不同步").
2. MCP 是正确的集成点, 不是选择题.
3. 第一个楔子是 API schema 同步, 其他场景是扩展.
4. 自用工具, npm 分发即可.
5. Claude Code agent teams 的抽象 (team / task list / mailbox) 可以直接移植.
6. TypeScript + Fastify daemon, Rust 是后备方案.

## 方案对比

### Approach A: 最小可行 - 直接移植 agent teams
**MCP 工具集 (含签名草稿, 用 zod)**:
- `register_agent({ model: string, role: string, display_name?: string, team?: string = 'default' }) -> { agent_id: string, team: string }` (agent_id 即 MCP session UUID, daemon 返回确认; 同 session 重复调用做 upsert metadata)
- `send_message({ to_agent_id?: string, to_role?: string, body: string, subject?: string }) -> { message_id: string, event_id: number, recipients: string[] }` (二选一, 同时传 role 优先; 离线 agent 消息入 events 表, 下次该 agent 查询时能读到)
- `broadcast({ body: string, subject?: string }) -> { message_id: string, event_id: number, recipients: string[] }` (**不含发送者自己**; 离线 agent 消息同样入 events 表)
- `list_agents({ team?: string }) -> { agents: Array<{ agent_id, role, display_name?, model, last_seen_at, online: boolean }> }` (team 默认查询者所在 team)
- `get_inbox({ since_event_id?: number, limit?: number = 50 }) -> { messages: Array<{ id, event_id, from_agent_id, from_role, subject?: string, body, sent_at }>, has_more: boolean, last_event_id: number }` (通过 event_id cursor 翻页; 无 mark_read 概念 - 客户端自己记 cursor)
- `task_add({ title: string, description?: string, depends_on?: string[] }) -> { task_id: string }`
- `task_claim({ task_id: string }) -> { ok: true } | { error: 'already_claimed' }`
- `task_complete({ task_id: string, result?: string }) -> { ok: true }`
- `task_list({ status?: 'pending'|'in_progress'|'completed' }) -> { tasks: [...] }`

**工作量**: S (1-2 天)
**优势**: 抽象已被 Claude Code 验证, 通用不预设场景
**劣势**: 用户的契约同步痛点需要 agent 自觉去 broadcast, 不稳定

### Approach B: 楔子优先 - A 的基础上把 API contract 做成一等公民
**附加工具 (含签名草稿)**:
- `register_contract({ name: string, schema: object, format?: 'jsonschema'|'openapi' = 'jsonschema', note?: string }) -> { name, version: number, diff?: ContractDiff }` (version 自动递增, 用 SQLite 事务 + SELECT MAX(version) FOR UPDATE 保证并发安全; 返回与上一版的 diff)
- `subscribe_contract({ name: string }) -> { ok: true, current_version: number }` (订阅持久化到 SQLite, daemon 重启后保留)
- `get_contract({ name: string, version?: number }) -> { name, version, schema, format, registered_at }`
- `diff_contracts({ name: string, from_version: number, to_version: number }) -> ContractDiff`
- `pending_contract_events({ since?: string }) -> { events: Array<{ contract_name, version, diff, emitted_at }> }` (轮询端, 用于 client 不支持 SSE push 时补齐离线期间变更)

**ContractDiff 格式** (明确定义, **深度 diff**):
```
{
  added_fields: Array<{ path: string, type_summary: string }>,
  removed_fields: Array<{ path: string, type_summary: string }>,
  changed_fields: Array<{
    path: string,
    from: { type?: string, required?: boolean, enum?: any[], raw: any },
    to:   { type?: string, required?: boolean, enum?: any[], raw: any }
  }>,
  breaking: boolean   // removed_fields 非空 | required 由 false→true | type 不兼容变更
}
```
`path` 用 JSON Pointer 风格 (`/properties/user/id`). `raw` 字段给出原始 JSONSchema 片段用于不能被结构化的变化. 首期实现可用社区库 (如 `json-diff-kit` 或 `json-schema-diff-validator`) 抽底层, 不自己造.

**推送策略 (现实主义, 事件入 events 表为真相源)**:
1. `register_contract` 成功 → 一律写统一的 `events` 表 (event_type='contract_registered', event_id 全局递增)
2. daemon 内部维护 `session_id -> agent_id + team` 映射, 对每个在线 SSE 会话按 team 过滤广播事件
3. agent 每次新任务启动前或定期调 `pending_contract_events({ since_event_id })`, 以该 agent 自己的 cursor 为准拉取, 推送只是速度优化
4. client cursor 去重: agent 收到 SSE 事件或 polling 结果, 都用 `last_processed_event_id` 判定去重, 不重复消费
- 这样 daemon 重启不丢事件, agent 离线后再上线能补齐, SSE 失败不影响一致性, 消息/任务将来要订阅也复用同一张 events 表

**工作量**: M (3-4 天)
**优势**: 直接击中核心痛点, 不依赖 agent 自觉
**劣势**: schema 格式首期只选 JSONSchema, OpenAPI / proto 延后

### Approach C: 上下文广播层 - 环境感知式
**工具集**: `post_status`, `get_team_snapshot`, `subscribe_since`
每个 agent 一轮后自动 post_status, 新任务前 get_team_snapshot
**工作量**: S-M (2-3 天)
**优势**: 对 prompt 要求最低, 最贴近"ambient awareness"本质
**劣势**: 无任务抽象, 分工协作弱

## 推荐方案: 混合 A → B (分两期)

**第一期 (MVP, 2 天): Approach A**
- **events 表 (outbox)**: `events(event_id INTEGER PRIMARY KEY AUTOINCREMENT, team TEXT NOT NULL, event_type TEXT NOT NULL, actor_agent_id TEXT, payload TEXT /*JSON*/, created_at TEXT)`. 所有被发布的事件 (消息 / 任务状态 / contract 变更) 统一走这张表.
- **agents 表**: `agents(agent_id TEXT PK, team TEXT NOT NULL, role TEXT, display_name TEXT, model TEXT, registered_at TEXT, last_seen_at TEXT)`. `register_agent` 用 INSERT OR REPLACE; 若 agent_id (MCP session UUID) 重复但来自不同 TCP session → 409.
- **messages 表**: `messages(id PK, event_id FK→events, team, from_agent_id, to_agent_id?, to_role?, subject?, body, sent_at)`. 实际是 events 的投影视图, 方便按 to_role 查询. 每写 message 时同时写 events 行.
- **tasks 表**: `tasks(id PK, team, title, description?, status, depends_on JSON, claimed_by?, claimed_at?, completed_at?, result?)`. `task_claim` 用单语句 CAS: `UPDATE tasks SET status='in_progress', claimed_by=? WHERE id=? AND status='pending' AND NOT EXISTS(SELECT 1 FROM tasks d WHERE d.id IN (depends_on JSON array) AND d.status != 'completed')`. 状态变更入 events.
- **错误路径**: daemon 不可达 → MCP client 收 connection refused; 同 session_uuid 重复 → 409; 寻址未注册 agent → `{ error: 'unknown_recipient' }`; 不在任一 team 的 agent 调 list_agents → 返回空数组.
- **目标**: 三个 agent 在同一 team 里注册 / 发消息 / 领任务 / 标完成
- **验证标准**: 阶段 0 先写 echo MCP tool 验证三家 agent 的 HTTP MCP client 都能连上; 再跑完整 A 的 e2e (Claude Code 发消息给 opencode, opencode 领任务, Codex 看到状态变化)

**第二期 (完整楔子, 额外 3 天): Approach B 叠加**
- 实现 contract primitive (见 Approach B 签名)
- 推送策略见 B 部分: SSE 尝试 push + `contract_events` 表持久化 + 客户端可轮询 `pending_contract_events`
- schema 格式: 首期只支持 JSONSchema, OpenAPI / proto 延后
- 目标: 后端 agent 每次改 API 调 `register_contract`, 前端 agent 启动新任务前调 `pending_contract_events` 自动拿到 diff
- 验证标准: 后端 agent 改 schema 字段, 前端 agent 不用人工提醒就能知道改了哪里 + offline 期间 daemon 重启后订阅仍然有效

**为什么混合**: A 提供基础设施 (agent identity / messaging / task), B 的 contract 层是在 A 之上的专用抽象. 先 A 打通全链路风险低, 再 B 直接对准痛点. 如果 A 不够用 B 也做不对.

## 分发计划

- **打包**: TypeScript 源码 → `tsup` 打包 → npm 发布
- **启动**: `npx ts-agent-teams daemon --port 9100 [--token <secret>]` - 仅监听 127.0.0.1
- **Daemon 生命周期**:
  - 启动时在 `~/.ts-agent-teams/daemon.pid` 记录 pid + port. 若已存在且进程存活 → 报错退出 (带提示 `--force` 覆盖)
  - 端口被占 → 递增试 9100/9101/9102, 三次失败退出并提示
  - 优雅停止: `npx ts-agent-teams stop` (发 SIGTERM, 刷 SQLite, 关闭 SSE 连接, 清 pid 文件). SIGINT/SIGTERM 信号做同样处理
- **配置**: `~/.ts-agent-teams/config.json`, agent 在各自配置中加入 MCP server 条目 (HTTP URL + agent_id query param)
- **I/O 性能约束**: `better-sqlite3` 是同步 API, 搭配 Fastify 异步需避免事件循环阻塞. 所有 DB 操作包在 `setImmediate` 或单独 worker 线程里, 单条查询 <1ms 的直接同步是可接受的.
- **CI/CD (稳定后)**: 初期手动 `npm publish` 即可, MVP 不做 GitHub Actions.
- **README 需要包含**: opencode / Claude Code / Codex CLI 三份配置示例片段 (含 token 传递写法)

## 开放问题 (MVP 不阻塞)

1. **Team 多实例**: 第一期只支持单 team (所有 agent 默认都在一个 team 里). cwd 分组 / 显式 team name 延后到第三期.
2. **消息/任务持久化保留期**: MVP 无限保留. 30 天归档策略延后.
3. **OpenAPI / proto schema 格式支持**: 第二期只实现 JSONSchema, 其他格式延后.
4. **Schema format 识别**: `register_contract` 当前用显式 `format` 参数. 后续若做自动探测需要独立设计.

## 成功标准 (可验证)

- 三个不同 agent (opencode + Claude Code + Codex CLI) 都能通过 HTTP MCP 连上同一个 daemon 并互发消息 (Phase 0 验证)
- 后端 agent 改 schema 后调 `register_contract`, 前端 agent 下一次 tool call 主动调 `pending_contract_events` 即可拿到 diff, 用户不手动转达
- 启动一条命令: `npx ts-agent-teams daemon`
- 每个 agent 的 MCP 配置 ≤ 5 行 JSON (跨三家 agent 都验证)
- 度量口径: 在一个真实项目 (比如自己的小项目) 连用 ts-agent-teams 一周, 记录"手动在 agent 之间复述信息"的次数, 对比未使用前; 目标减少 ≥ 50%

## Reviewer Concerns (评审遗留, 实现到相关阶段时补齐)

**不阻塞 MVP (阶段 0+1+2 的 Approach A), 主要影响阶段 3 的 contract 层:**

1. **`breaking` 判定规则**: "type 不兼容" 需细化 (string→number 算? 精度放宽/收紧?). 实现阶段 3 时先定一套最保守规则 (任何 type 字符串变更 + required false→true + 移除字段 = breaking), 之后迭代.
2. **`send_message` 到离线 agent**: ✅ 已由 /plan-eng-review 改为**一律入 events 表**, 上线自然拉到. 不再是 concern.
3. **`task_claim` 的 `already_claimed` error**: 补齐返回当前 owner (`{ error: 'already_claimed', owner: string }`).
4. **`task_complete` 权限**: 非 claimer 调用返回 `{ error: 'not_owner' }`. `depends_on` 未完成的任务不允许 claim. ✅ 后半部分已整合进 task_claim CAS 的 SQL 条件.
5. **`get_inbox.since` 类型**: ✅ 已由 /plan-eng-review 改为 `since_event_id: number`.
6. **`contract_events` per-subscriber cursor**: ✅ 已由 /plan-eng-review 改为 client 侧 cursor, 服务端无订阅 cursor 状态.
7. **token 鉴权失败**: HTTP 401 + body `{ error: 'invalid_token' }`. agent_id 与 session 不匹配返回 403.
8. **并发 `register_contract` 同 name**: SQLite 事务串行化, 两次调用串行递增版本, 各自返回自己的 version 和相对前一版的 diff.
9. **~~JSONL 事件日志 schema~~**: ✅ JSONL 已由 /plan-eng-review 废弃, 统一成 events 表.
10. **JSON Pointer 示例修正**: 嵌套字段应写作 `/properties/user/properties/id`, 不是 `/properties/user/id`.
11. **stdio-proxy Plan B 细节**: 若阶段 0 发现某 agent 不支持 Streamable HTTP, 写一个 ~100 行的 stdio MCP server (同仓一个子包), 把 stdio tool call 转发到 HTTP daemon. 接口层面对 agent 透明.
12. **better-sqlite3 策略**: 单条读写 <1ms 直接同步, 批量或 contract diff 计算用 `node:worker_threads`. 阶段 1 压测后定阈值.
13. **阶段 3 工期**: 评审认为 3 天偏紧, 可能 4-5 天. 计划时按 5 天上限保险.

**Eng Review 新增**:
14. **events 表 7 天自动清理**: daemon 内部 `setInterval` 每 1 小时跑 `DELETE FROM events WHERE created_at < datetime('now','-7 days')`. contracts/tasks/agents 三张当前态表不清理.
15. **`team` 字段 MVP 就支持**: 所有表加 `team TEXT NOT NULL DEFAULT 'default'` 列, 所有查询 WHERE team 过滤.
16. **Phase 0 连通性 e2e test 硬前置**: `tests/e2e-connectivity.test.ts` 必须在任何业务 tool 实现前通过. 这是最大风险, 失败直接回去改 transport 方案.

## Eng Review 附录

### NOT in scope

- Remote/non-local daemon 部署 (daemon 锁死 127.0.0.1)
- 多用户/多租户 (单用户本机工具)
- OAuth / API key 轮换 (仅本机 token 鉴权)
- OpenAPI / proto 等非 JSONSchema 格式 (Phase 3 之后)
- Contract 的语义化 diff (只做结构化 diff, 不理解业务含义)
- Contract 历史的 UI 展示 (SQL 查询 + 用户自己写辅助工具)
- CI/CD 自动发版 (稳定后手动)
- Cross-machine agent 协作
- Agent 本身的沙箱/权限控制 (信任所有本机 agent)

### Worktree parallelization strategy

依赖表:

| Step | Modules touched | Depends on |
|------|----------------|------------|
| Phase 0 连通性探针 | `src/daemon/`, `src/mcp/echo.ts` | — |
| Phase 1a: events + agents | `src/storage/`, `src/mcp/register_agent.ts` | Phase 0 |
| Phase 1b: messages (mailbox) | `src/mcp/send_message.ts`, `src/mcp/broadcast.ts`, `src/mcp/get_inbox.ts` | Phase 1a |
| Phase 1c: tasks | `src/mcp/task_*.ts` | Phase 1a |
| Phase 2 真实集成 | `docs/configs/`, 无代码 | Phase 1b + 1c |
| Phase 3a: contracts core | `src/mcp/register_contract.ts`, `src/mcp/get_contract.ts` | Phase 1a |
| Phase 3b: SSE + polling | `src/daemon/sse-fanout.ts`, `src/mcp/pending_contract_events.ts` | Phase 3a |

Lane 分组:
- **Lane A (sequential)**: Phase 0 → 1a → 1b → Phase 2 验证消息流
- **Lane B (parallel after 1a)**: 1a → 1c (tasks 与 messages 独立, 只共享 events 表的 append 接口)
- **Lane C (parallel after 1a)**: 1a → 3a → 3b (contracts 独立于 mailbox/tasks)

执行顺序建议:
1. Lane A 先跑 Phase 0 + 1a (串行, 核心基础)
2. 1a 完成后 Lane A 的 1b, Lane B 的 1c, Lane C 的 3a 可并发 (三个 worktree)
3. 全部汇合后 Phase 2 集成验证 + 3b SSE 补齐

**Conflict flag**: Lane B 的 1c 和 Lane A 的 1b 都会修改 `src/storage/events-outbox.ts` 追加事件的接口. 建议 1a 阶段把 `EventsOutbox.append()` 写死并充分测试, 之后 1b/1c 只作为调用方不改接口; 否则两 lane 并发会合并冲突.
